## 1. Introduction：研究背景与问题定义

这一章回答“为什么值得做”。

内容包括：

- 金融异常检测的应用场景：市场监控、风险预警、事件调查。
- 实时流的困难：高频、噪声、概念漂移、不同交易时段、数据质量。
- 旧方案的问题：四模型分数难解释、模型职责重叠、实时成本较高。
- 核心研究问题。

建议明确三个 Research Questions：

- RQ1：轻量、可解释的市场因子能否替代冗杂的模型集成，完成实时异常检测？
- RQ2：CEP 对持续、反转、新闻确认和跨资产等序列异常是否比点检测更合适？
- RQ3：在严格的事件级评测下，系统能否同时满足检测质量、低告警负担和实时延迟要求？

本章最后列出贡献：

1. 统一的 live/replay 市场事件模型。
2. 八个有金融含义的增量因子。
3. 六类具有方向和时间语义的 CEP 模式。
4. 可追溯、可去重的告警结构。
5. 避免数据泄漏的一对一事件级评测。
6. 真实 Alpaca、12 个月数据和 Kafka 端到端验证。

## 2. Literature Review：跨领域异常检测综述

不要逐篇罗列论文，而是按“这个领域给本项目什么启发”来组织。

### 2.1 医疗预警

- 少量关键指标。
- 分段风险评分。
- 持续条件比单次越界更可靠。
- 告警疲劳问题。

对应到项目：普通单因子变化不直接告警，需要持续或多因素确认。

### 2.2 工业与航天监测

- 派生量比原始传感器值更有意义。
- 运行状态和工况基准。
- 残差、置信度和可追溯诊断。

对应到项目：使用相对成交量、市场残差、价差压力，而不是只用原始价格和成交量。

### 2.3 网络安全

- 流式计数、比例和 bounded state。
- 单个事件可能正常，但事件组合可能异常。
- 事件关联和图结构。

对应到项目：使用有限状态和 CEP 表达持续压力、新闻确认、跨资产冲击。

### 2.4 通用时序异常检测

- 统计方法、在线树、深度模型。
- 简单方法在大型基准上仍然有竞争力。
- 评测协议可能比模型复杂度更影响结论。

对应到项目：不默认深度模型更优，重点控制数据泄漏、事件匹配和负对照。

### 2.5 金融异常检测

- 价格、成交量、流动性、订单压力。
- 市场共同波动与个股特异性波动的区别。
- 新闻时间和价格确认关系。

最后形成一个综合表：

| 跨领域结论           | MarketStream 设计                |
| -------------------- | -------------------------------- |
| 少量可解释指标       | 八个轻量因子                     |
| 持续条件减少误报     | sustained pressure               |
| 派生量和运行基准     | relative volume、market residual |
| 事件关联             | 六类 CEP 模式                    |
| 控制告警疲劳         | 冷却、合并和去重                 |
| 评测比模型堆叠更重要 | 一对一事件匹配和时间切分         |

## 3. Problem Formulation and Requirements：问题形式化

这是体现学术完整性的关键章节。

需要定义：

- 什么是 `MarketEvent`。
- 什么是 `FactorSnapshot`。
- 什么是异常事件，而不只是异常点。
- 什么情况下产生正式告警。
- live 和 replay 的一致性要求。
- 数据质量与暖机状态如何影响告警。

可以正式定义一个告警：

\[ A_t = g(F_t, F_{t-k:t}, C_t, Q_t) \]

其中：

- \(F_t\)：当前因子状态。
- \(F_{t-k:t}\)：历史窗口中的因子序列。
- \(C_t\)：市场、时段和新闻上下文。
- \(Q_t\)：数据质量及暖机状态。
- \(g\)：CEP 模式和告警语义。

你的核心观点是：异常不是简单的 \(x_t>\theta\)，而是上下文相关的事件判定。

## 5. Methodology：轻量因子与 CEP 方法

这是报告最核心的一章。

### 5.1 因子设计原则

先写原则，再写公式：

- 因子应有金融含义。
- 因子组尽量正交。
- 使用增量统计和有界状态。
- 按 ticker、交易时段和日内位置建立基准。
- 当前样本不能参与自己的阈值计算。

### 5.2 八个因子

每个因子都按照同一个结构描述：

1. 经济或市场含义。
2. 输入事件。
3. 计算公式。
4. 基准和阈值。
5. 可能的误报情况。
6. 在 CEP 模式中的用途。

例如市场残差：

\[ \text{market\_residual}_{i,t} = r_{i,t}-r_{\text{benchmark},t} \]

它用于区分：

- 个股独立异动；
- 整体市场共同上涨或下跌。

### 5.3 鲁棒基准

介绍 median、MAD 和经验分位数：

\[ z^{robust}_{t} = \frac{x_t-\operatorname{median}(X)} {1.4826\cdot \operatorname{MAD}(X)+\epsilon} \]

强调：

- 不假设金融数据服从正态分布。
- 盘前、正常交易、盘后分别建基准。
- 暖机不足时不发普通告警。
- 阈值在测试集前冻结。

### 5.4 六类 CEP 模式

每个模式应包含：

- 金融意义。
- 事件顺序。
- 最大时间间隔。
- 方向。
- 触发因子组。
- 负对照。

例如：

```
news_shock(up)
    → within 5 minutes
return_surprise(up)
    → news_confirmed_move(up)
```

不要只写“代码实现了六个规则”，而要解释为什么选择这六类，它们分别解决什么单点检测无法解决的问题。

### 5.5 告警语义

说明：

- 原子事件不等于正式告警。
- 正交因子确认。
- 持续条件。
- 极端单因子例外。
- ticker/pattern/direction 冷却。
- 告警合并和确定性去重键。

## 6. Experimental Design：实验设计

这一章要突出实验可信度。

### 6.1 数据

- 五个标的：AAPL、TSLA、NVDA、QQQ、SPY。
- 400 天历史覆盖。
- OHLCV 1,385 行。
- Alpaca/Benzinga 新闻 15,148 条。
- IEX 实时 trade、quote、bar。
- 合成序列异常和负对照。

### 6.2 时间切分

使用严格的 60/20/20：

- 训练段：建立基准。
- 验证段：选择阈值。
- 测试段：冻结后只评测。

说明为什么不能随机切分金融时间序列。

### 6.3 实验组

至少包括：

1. CEP 主方法。
2. 简单单因子阈值。
3. 旧四模型 ensemble。
4. CEP 去除时间关系。
5. 因子组消融。
6. 新闻消融。
7. 微观结构消融。

### 6.4 异常与负对照

六类正样本对应六类 CEP 模式。

负对照包括：

- 高成交量但价格不动。
- 市场整体共同波动。
- 陈旧新闻。
- 盘后价差扩大。
- 只有价格变化但没有流动性压力。
- 新闻出现但价格未确认。

### 6.5 指标

主指标：

- 事件级 precision、recall、F1。
- 首次检测延迟。
- 每 ticker 每小时告警数。
- 重复告警率。
- p50、p95、p99 系统延迟。
- Bootstrap 95% 置信区间。

强调一对一向前匹配：

- 检测不能早于事件开始。
- 一条告警不能重复匹配多个事件。
- 旧 ±2 window 只作为敏感性分析。

## 8. Discussion：自己的观点、反思与局限

这一章最能体现“不是只完成了一个工程项目”。

建议提出四个核心观点。

### 观点一：复杂性应该放在事件表达，而不是模型数量

旧方案的复杂性来自四个模型和权重；新方案的复杂性来自金融语义、时间关系和上下文。后者更容易解释和验证。

### 观点二：异常是相对于运行状态的偏离

相同的价差扩大：

- 正常交易时段可能异常；
- 盘后可能正常。

因此异常阈值不能脱离 session 和日内位置。

### 观点三：检测准确率不是唯一目标

实际系统还需要考虑：

- 告警负担。
- 重复率。
- 检测延迟。
- 数据质量。
- 可追溯性。
- 失败时是否可解释。

### 观点四：可靠评测可能比增加模型更有价值

如果测试数据参与阈值选择，或者允许检测发生在事件之前，再高的 F1 也没有意义。你的贡献之一是把评测协议做得更接近真实在线场景。

局限应主动写：

- IEX 不是完整 SIP。
- 当前标的数量有限。
- 新闻情绪使用轻量词法方法。
- 真实异常标签本身存在主观性。
- 微观结构历史数据覆盖仍有限。
- 极端单因子规则可能在负对照中产生误报。
- 当前前端主要是调试界面。

## 9. Conclusion and Future Work：结论与未来工作

结论不要只重复“系统完成了”。

建议回答三个研究问题：

- 轻量因子是否可行？
- CEP 是否为序列异常提供了额外价值？
- 系统是否满足实时和可追溯要求？

未来工作按价值排序：

1. 使用 SIP 或更完整的订单簿数据验证。
2. 扩大标的和市场范围。
3. 建立更完整的真实事件标注集。
4. 学习自适应但仍可解释的阈值。
5. 将 ML 放在 shadow 或二阶段调查，而不是阻塞实时检测。
6. 重构专业前端，支持告警调查和系统健康监控。
