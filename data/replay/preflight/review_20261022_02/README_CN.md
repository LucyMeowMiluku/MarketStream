## 已发现的计分与复现风险

1. `replay/evaluator.py` 的 CEP 仅将 `interval.ticker` 告警纳入评分，而 IF 接收全部上下文快照，
   结果未过滤为被审阅标的。直接比较会让 IF 的上下文告警成为额外 FP。正式比较前必须修复并验证。
2. IF 目前对逐窗口异常直接报警；CEP 有质量/暖机门和 cooldown。必须预先声明比较的是各自原生策略，
   还是共同策略，保存原始逐点分数与抑制前后告警。不能只凭“八因子相同”宣称所有输入和策略相同。
3. CEP 原始 trace 有模式 completed/in_progress 和 explanation，但没有完整逐条机器内部状态转换日志；
   IF 当前没有写入逐窗口 score、模型与 scaler 工件。FP/FN 完整追溯前还需补齐这些输出。
4. 现有 run manifest 不包含完整实际代码快照或所有环境派生参数，且相同 run_id 可能覆盖目录；
   正式运行必须使用新目录并保存冻结快照、参数、环境与失败记录。
5. baseline 日数和文件 hash 不能证明覆盖完整；每个标的/周期/时间槽的因子历史数量和 ready 状态需逐项验证。
6. 开盘跳空和窗口内方向可能相反。现有因子从区间开始积累，无法自动假定它能看见隔夜跳空；
   必须预先定义方向、上下文预热和“检测什么”，否则此类 FN 无法解释。
